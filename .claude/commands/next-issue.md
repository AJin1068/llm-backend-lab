argument-hint: "[PR 번호] (예: 4, 14a. 생략하면 ready 라벨이 붙은 열린 Issue 중 PR 번호가 가장 작은 것)"
---

이 레포의 개발 세션으로 일한다. CLAUDE.md의 "작업 순서"를 그대로 따른다.

대상: $ARGUMENTS
(비어 있으면 `ready` 라벨이 붙은 열린 Issue 중 제목의 "PR N" 번호가 가장 작은 것을 고른다. Issue 번호(`#13`)가 아니라 제목의 PR 번호로 고른다. 번호가 같으면 1 < 1c < 1d < 1e < 2, 14a < 14b 순서다. `ready` Issue가 없으면 그렇게 말하고 멈춘다. 번호를 직접 줬는데 `ready`가 아니면, 비어 있는 칸(범위·하지 않을 것·완료 기준·정해진 결정·참고 문서)을 알려 주고 멈춘다. Issue를 채우는 건 기획(Claude 앱)이 한다.)

0. `git checkout main && git pull origin main`으로 최신 `main`을 받는다. 커밋 안 된 변경이 있으면 멈추고 알린다.
1. `gh issue list --state open --label ready`로 대상을 고른다. `gh issue view <번호> --comments`로 본문과 코멘트를 읽는다.
2. CLAUDE.md, 대상 Issue의 "참고 문서"(`docs/prd.md`, `docs/design.md`, `docs/eval-plan.md`, `docs/adr/`의 해당 절), 손댈 코드를 읽는다. 직전에 merge된 PR 설명(`gh pr list --state merged --limit 3`)의 "다음에 할 것"·"확인 필요" 중 이 Issue에 걸리는 것을 확인한다. `eval/`은 읽기만 한다.
3. 계획을 보여 주고 **승인을 기다린다.** 계획에는 바꿀 파일(빠짐없이), 접근 방법, 대안 1개와 트레이드오프, 완료 기준을 어떻게 확인할지, 사람이 정해야 할 것을 담는다. 승인 전에는 코드를 쓰지 않는다.
   - **질문은 줄인다.** Issue 본문·코멘트("정해진 결정" 포함)·문서·ADR에 답이 있으면 묻지 않고 계획에 "정해진 대로: …(출처)"로 적는다. 함수 이름, 파일 배치, 테스트 방법처럼 개발이 정할 수 있는 건 묻지 않고 계획에 적는다.
   - 답이 없는 것만 "정할 것" 칸에 모아 **한 번에** 묻고, 하나마다 추천안과 이유를 붙인다.
   - Issue와 설계 문서에 없는 새 단계·외부 서비스·DB 구조·화면이 필요하면 계획에 넣기 전에 먼저 묻는다.
4. 승인되면 `main`에서 `<종류>/pr<번호>-<짧은 설명>` 브랜치를 만들고 CLAUDE.md 4~7단계(구현 → `uv run pytest`·ruff → PR 템플릿 채우기 → `Closes #<Issue 번호>`)를 따른다. merge는 하지 않는다.
5. 끝나면 결과를 **한국어로, 쉬운 말로** 보고한다: 무엇을 했는지, 완료 기준 결과, PR 링크, 사람이 답해야 할 질문.
6. PR이 merge된 뒤 다시 부르면 다음 Issue의 계획까지만 보여주고 승인을 기다린다.

## 기획이 바뀐 경우 (처음부터 다시 하지 않는다)

대상 Issue를 이미 계획했거나 브랜치가 있으면, 0단계 뒤에 지난번 이후 바뀐 것을 확인한다.
- Issue 본문·코멘트 변경, `main`의 `CLAUDE.md`·`docs/`·`eval/` 변경(`git log`/`git diff`로 지난번 읽은 커밋 이후).
- 브랜치가 있으면 `main`을 그 브랜치에 merge한다(rebase·force push 금지).

그다음 아래 표만 보여 주고 **바뀐 부분만** 승인을 받는다. 바뀌지 않은 부분은 다시 묻지 않는다.

| 바뀐 것 | 이미 한 계획·구현에 주는 영향 | 고칠 것 / 그대로 둘 것 |
| --- | --- | --- |

- 이미 만든 코드와 테스트는 버리지 않는다. 바뀐 요구에 맞지 않는 부분만 고친다.
- 완료 기준이 바뀌었으면 측정을 다시 돌린다.
- 사람은 "계속해줘" 또는 `/next-issue <PR 번호>`만 말하면 된다.
