# ADR-0005. 개발 과정의 벽은 역할 수가 아니라 기계로 지킨다

- 상태: 승인됨
- 날짜: 2026-11-11
- 결정자: 서아진

## 맥락

이전 프로젝트(patent-rag)는 기획·개발·검증 3역할로 나눠 PR 8개에 24차수를 돌았다. 원인 1순위는 지시서 빈틈이었고, CI가 없어서 "채점 코드를 못 고친다"를 지침과 검증의 눈으로만 지켰다. 이번에는 PR 21개를 16일 안에 해야 한다.

## 결정

"누가 무엇을 못 보고 못 고치는가"를 기계가 지키게 한다.

- CI `eval-guard`: `eval/`로 시작하지 않는 브랜치의 PR이 `eval/`을 바꾸면 실패
- CI `agent (pytest + ruff)`
- `.claude/settings.json` deny: merge·승인·main push·강제 푸시·`.env` 읽기
- GitHub main 규칙: PR 필수, 삭제·강제 푸시 금지, 이후 CI 통과 필수
- 규칙은 레포 루트 `CLAUDE.md` 한 곳에만 둔다
- 홀드아웃 시나리오는 레포와 claude.ai 프로젝트 밖(맥북)에 둔다

검증 세션은 숫자가 나오는 PR(5, 15, 17, 19, 21)에만 돌린다. 채점 규칙은 별도 세션이 규칙 문서만 보고 테스트를 써서 빈틈을 찾는다.

## 검토한 대안

- patent-rag 방식 그대로(모든 PR에 3역할): 같은 비율이면 60차수 이상으로 11/22를 못 맞춘다.
- 검증 없이 개발 세션만: 점수가 실력인지 채점표를 고친 결과인지 알 수 없다.

## 결과

- 좋은 점: 점수 없는 PR(DB, 화면, 뼈대)은 오가는 비용 없이 간다. 벽이 거의 공짜로 선다.
- 나쁜 점: 점수 없는 PR의 설계 실수는 코드 리뷰에만 기댄다. 규칙을 독립적으로 읽는 쪽은 채점 규칙 테스트를 쓰는 세션 하나뿐이다.
